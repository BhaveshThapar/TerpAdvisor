PRODUCT REQUIREMENTS DOCUMENT
TerpAdvisor
Intelligent Course Recommendation Engine for UMD Students

Author: Bhavesh Thapar Version: 3.1  |  April 2026 Status: In Progress

1. Executive Summary
TerpAdvisor is a full-stack web application that provides personalized course recommendations to University of Maryland students. It combines a dynamic per-major prerequisite DAG, a hybrid multi-scorer recommendation pipeline, CSP-based schedule optimization, an Easiest Classes discovery mode, and a three-tier cache to deliver intelligent, degree-aware course guidance.

Version 3.1 of this document reflects the Dynamic Catalog update. The backend no longer hardcodes per-major course graphs or requirement trees — both are now derived at request time from the seeded UMD catalog and a new majors table. Key additions: a umd.io prerequisite parser that builds PrereqNode trees from upstream JSON, a dynamic CourseGraph.build_from_umd_catalog() that selects relevant departments from the loaded requirements, a majors table (Alembic migration a1b2c3d4e5f6) seeded via scripts/seed_majors.py, a requirements_loader with 1-hour TTL cache and graceful fallback, a GET /api/majors endpoint powering a dynamic onboarding dropdown, recommendation section grouping ("Major Requirements" vs "Other Courses") with fulfills_requirements badges, and a show_prerequisites_only filter on /api/recommendations. Test suite is at 84 passing tests (up from 63 in v3.0). The frontend onboarding page now sources majors and tracks directly from the backend, and the recommendations page groups results and exposes the prerequisite-only toggle.

2. Problem Statement
Course selection at UMD remains fragmented and time-consuming. Students must cross-reference:
Testudo for course availability and seat counts
PlanetTerp for GPA, grade distributions, and professor reviews
Academic catalog PDFs for degree requirement trees
Word-of-mouth for scheduling wisdom (no 8AMs, avoid certain professors)

No single tool answers: "Given what I have taken, what I need, and how I like to learn — what should I take next semester?" TerpAdvisor solves this.

A specific pain point that motivated v3.0: students who have already completed their GenEd requirements and just need easy elective credits to stay enrolled have no tool to quickly identify low-stress courses from outside their major. TerpAdvisor's Easiest Classes mode directly addresses this.

3. Target Users
3.1 Primary Persona
UMD undergraduates (CS, Math, Engineering) actively planning their next semester and wanting data-driven, requirement-aware recommendations.

3.2 Secondary Personas
Transfer students mapping remaining requirements quickly via transcript upload
Students who have finished their GenEds and want easy elective credits (GPA-booster courses, online/async offerings)
Students exploring minors or electives outside their department
Advisors and peer mentors using it as a quick reference tool

5. Core Features

5.1 Transcript Parsing & Course History Input
Students can populate their course history via three methods:
Manual search: autocomplete by department/code (e.g., CMSC216, MATH241) backed by the full UMD course catalog
Transcript text paste: paste raw text from Testudo's unofficial transcript; the backend regex parser extracts all completed courses, credits, grades, and gen-ed tags automatically
PDF upload (POST /api/courses/parse-transcript-pdf): upload an unofficial transcript PDF; the server extracts text via PyMuPDF and runs the same parser

The parser handles edge cases including: repeated courses (most recent grade wins), withdrawals (W/AW/XF excluded), AP/transfer equivalency credits (mapped to UMD course IDs where possible, or stored as TR_<credits>_<name> tokens), and in-progress courses (tagged separately for corequisite checking).

5.2 Degree Requirement Tracking & Audit
POST /api/audit runs a full degree audit against the student's completed courses. As of v3.1, requirements are seeded into the majors table via backend/scripts/seed_majors.py and loaded at request time through backend/app/engine/requirements_loader.py (1-hour TTL in-process cache; falls back to in-memory MAJOR_BUILDERS on DB miss; falls back to Computer Science as last resort). Any major added to the majors table works end-to-end (recommendations, audit, plan) without code changes.
Seeded majors at launch:
Major | Tracks / Concentrations | GenEd Support
Computer Science B.S. | General, Data Science, Machine Learning, Quantum Information | Yes
Mathematics B.S. | General | Yes
Information Science B.S. | General | Yes
Economics B.A. | General | Yes
Biological Sciences B.S. | General | Yes
Mechanical Engineering B.S. | General | Yes

The audit result includes: overall progress %, credits completed vs. required, per-group and per-requirement status (completed / in_progress / partially_complete / not_started), remaining course options, and a list of the highest-impact courses (courses that satisfy the most remaining requirements).
Minor support: a minor_prefix field injects department-level 300/400-level courses into the Upper-Level Coursework (ULC) requirement automatically.

The audit engine is also called internally by the Easiest Classes mode to detect whether any GenEd requirements remain, allowing the recommendation candidate pool to be automatically narrowed to GenEd-satisfying courses when applicable.

5.2.1 Dynamic Catalog Architecture (New in v3.1)
Prior to v3.1, each supported major had a hand-written course graph builder inside app/api/recommendations.py. Adding a major meant writing ~50 lines of CourseNode/PrereqNode literals, and students whose major wasn't listed silently fell back to CS — hiding legitimate courses (e.g. INST155 never appeared for Info Sci students because the hardcoded INST graph only listed ~20 courses). v3.1 replaces all of that with dynamic DB-driven construction:

- Prerequisite parser (app/engine/prerequisite_parser.py): converts umd.io prerequisite JSON (and/or/coreq/nested structures, plain strings, and lists) into PrereqNode trees. Handles null/empty expressions gracefully.
- Dynamic graph builder (CourseGraph.build_from_umd_catalog in app/engine/course_graph.py): given a major and its loaded DegreeRequirements, extracts all department prefixes from requirements.groups[*].requirements[*].course_options and prefix_patterns, unions them with MATH/STAT/ENGL (gen-ed staples), queries the Course table for every course in those departments, and parses each course's prerequisites_raw into a PrereqNode. Logs an ERROR if the resulting course set is empty so that missing seeds are loud, not silent.
- Requirements loader (app/engine/requirements_loader.py): load_requirements_for_major(db, major, track) hits the majors table first (keyed by name + track, falling back to the General track if the specific track isn't seeded). On miss, logs a warning and rebuilds from the in-memory MAJOR_BUILDERS dict. On unknown major, logs a warning and returns CS. Results are cached in-process for one hour via a (major, track) keyed dict, avoiding repeated DB round-trips in the common case.
- Requirement serialization helpers: requirements_to_dict / requirements_from_dict round-trip DegreeRequirements through JSONB so the same in-memory tree can be stored in Postgres, cached in Redis if desired, and reconstructed without loss.
- Seed script (backend/scripts/seed_majors.py): walks MAJOR_BUILDERS, expands CS across its four tracks, and idempotently upserts each (name, catalog_year, track) row into the majors table. Safe to re-run after every catalog update.

5.4 Smart Recommendation Engine
POST /api/recommendations returns ranked courses with explainable scoring. The engine is built as a Strategy pattern: each scoring dimension is a pluggable Scorer implementing BaseScorer. Scores are aggregated with user-adjustable weights, then normalized to sum to 1.0.

The engine supports two goal modes set via the goal field:
- "balanced" (default): uses the standard weight distribution below, sourcing candidates from the dynamic per-major prerequisite DAG built via CourseGraph.build_from_umd_catalog().
- "easiest": sources candidates from the full UMD course catalog (all departments), auto-applies ease-oriented preference tags, and shifts weights heavily toward GPA and review-keyword matching. See Section 5.5 for details.

Additional v3.1 fields on POST /api/recommendations:
- show_prerequisites_only (bool, default false): when true, always restricts candidates to courses whose prerequisites the student has already satisfied — even in "easiest" mode, which would otherwise source from the full catalog. This is wired to a toggle in the recommendations-page sidebar.
- Response shape additions: every RecommendationResponse now carries `section: "major_requirement" | "other_course"` and `fulfills_requirements: list[str]`. These are computed post-scoring by DegreeAuditor.classify_courses (app/engine/degree_audit.py), which maps each recommended course against unmet requirement groups using the same course_options / prefix_patterns / GenEd-tag rules as the audit engine. The frontend uses these fields to split the recommendation list into two sections ("Major Requirements" and "Other Courses") with per-card badges for the requirement groups each course would fulfill.

Scorer | Default Weight (balanced) | Signal
Requirement Fulfillment | 35% | How many unmet degree requirements this course satisfies
GPA | 25% | Average grade from PlanetTerp grade distributions
Professor Rating | 15% | PlanetTerp professor avg_rating for sections being offered
Review Sentiment | 10% | NLTK-based positive/negative keyword analysis of student reviews
Schedule Fit | 10% | Absence of conflicts with already-selected sections (via interval tree)
Students Also Took | 5% | Co-enrollment frequency from aggregate grade data (collaborative filtering)
Preference Tags | ~0% default | Matches user-selected tags (see full tag list in Section 5.7)

Each recommendation is returned with a full explanation list (factor, score, weight, contribution, human-readable text) and a top_reason sentence derived from the highest-contributing factor.

5.5 Easiest Classes Mode (New in v3.0)
When the goal field is set to "easiest" on POST /api/recommendations, the engine enters a special mode optimized for finding low-stress, high-GPA courses across the entire UMD catalog.

Candidate pool: Instead of restricting to courses unlocked by the student's major prerequisite DAG, the engine queries the full Course table (all departments). The student's completed courses are excluded. This means ASTR, AASP, LING, KNES, and any other department can appear in results.

GenEd-aware narrowing: The engine internally runs a degree audit. If the student still has unmet GenEd requirements (e.g., DSHU, DVUP), the candidate pool is automatically narrowed to courses whose gen_eds tags intersect those unmet categories. This ensures "Easiest Classes" means "easiest courses that also fulfill your remaining graduation requirements." If all GenEds are satisfied, no narrowing is applied — the full catalog stands.

Auto weight override (Easiest mode, all GenEds done):
Scorer | Weight
GPA | 50%
Preference Tags | 30%
Review Sentiment | 10%
Requirement Fulfillment | 5%
Professor Rating | 5%
Collaborative / Schedule Fit | 0%

Auto weight override (Easiest mode, GenEds still unmet):
Scorer | Weight
GPA | 40%
Preference Tags | 30%
Requirement Fulfillment | 20%
Review Sentiment | 10%
Professor Rating | ~0%
Collaborative / Schedule Fit | 0%

User-supplied weight_overrides take precedence — so the UI sliders remain live in Easiest mode for power users who want to fine-tune.

Auto-injected preference tags when none are supplied by user:
["online", "no-attendance", "no-final-exam", "light-workload", "easy-a"]

These tags are soft boosts, not hard filters: courses without matching review keywords still appear if their GPA is high. This prevents empty result sets when review data is sparse.

5.6 Filter System
Filters are applied before scoring to narrow the candidate course set:
Filter | Values
departments | One or more department codes (e.g., CMSC, MATH)
levels | Course level buckets: 100, 200, 300, 400
gen_eds | Any combination of DSNS, DSHU, DSNL, DVUP, DVCC, SCIS, etc.
min_credits / max_credits | Credit range filter
min_gpa | Minimum average GPA threshold (e.g., 3.0)
exclude_courses | Specific course IDs to omit from results

Filters compose with both Balanced and Easiest goal modes. For example, a student in Easiest mode can additionally filter to only 100/200-level courses or exclude a specific department.

5.8 CSP Schedule Builder
POST /api/schedule/generate solves schedule construction as a Constraint Satisfaction Problem:
Variables: one slot per requested course
Domains: available sections for each course (from umd.io via DB)
Constraints: no time conflicts (checked via interval tree), hard time bounds (no_before, no_after), avoided days

Backtracking search with forward checking generates all feasible schedules (up to 10x the requested count), then ranks them by a 100-point preference score:
Factor | Points
Time preferences (penalize early/late classes) | 30
Day preference (MWF, TuTh, no-Friday, etc.) | 25
Gap minimization between back-to-back classes | 20
Daily balance (even class distribution) | 15
Seat availability | 10

POST /api/schedule/export/ical generates an iCal (.ics) file from the best schedule for direct import into Google Calendar or Apple Calendar (no account needed — just import the .ics). Events recur weekly for 16 weeks with the correct day-of-week mapping.

5.9 Multi-Semester Graduation Planner
POST /api/plan generates a semester-by-semester course plan to graduation. Algorithm:
Run degree audit to identify remaining required courses
Build a subgraph of remaining courses and topologically sort via Kahn's algorithm
Greedily assign courses to semesters respecting credit caps, course count caps, and prerequisite ordering
Prioritized courses (user-specified) are front-loaded into earlier semesters

Returns semester labels (e.g., "Fall 2026", "Spring 2027"), course lists, credit totals, and a warnings list for courses that could not be scheduled due to unresolvable prerequisites.

5.10 Course Detail View
GET /api/courses/:id returns a rich course detail payload:
Course description (from umd.io, backfilled and persisted on first request)
Average GPA and full grade distribution by letter grade (live from PlanetTerp)
Student reviews with rating and text
Professor list with ratings and review counts (from DB + PlanetTerp fallback)
Prerequisites with completion status relative to a passed completed= query param
Which degree requirement(s) in each supported major this course fulfills
Section meeting times, days, seat availability

5.11 Cart & Wishlist
Two lightweight persistence features:
Cart (POST/GET/DELETE /api/cart): courses the student intends to register for this semester. Used as the "selected_sections" input to the schedule solver for conflict detection.
Wishlist (POST/GET/DELETE /api/wishlist): saved courses for future semesters or further review.

6.4 Data Flow
0. (v3.1) Onboarding fetches GET /api/majors once on mount and populates the major dropdown; the student's selected major drives the track dropdown dynamically. Transcript-detected majors that don't exist in the seeded catalog trigger an amber "not in our catalog" warning and force a dropdown pick.
1. Student opens TerpAdvisor — no sign-in required. Onboarding collects major, track, optional minor, and course history (or transcript upload). All data is persisted to browser localStorage.
2. Frontend calls POST /api/audit -> backend loads requirements from the majors table via load_requirements_for_major (1-hour TTL cache, falls back to in-memory MAJOR_BUILDERS on miss, then to CS as a last resort), runs degree audit, returns progress %.
3. Frontend calls POST /api/recommendations with the selected goal ("balanced" or "easiest") -> backend dynamically builds the per-major course graph via CourseGraph.build_from_umd_catalog (derives department prefixes from the loaded requirements), resolves candidate courses (DAG or full catalog), applies filters, scores via all 7 scorers, then classifies each recommendation via DegreeAuditor.classify_courses so the response carries section + fulfills_requirements fields.
   - In "easiest" mode, backend also runs an internal audit to detect unmet GenEds and narrows candidates accordingly.
4. Student adjusts weight sliders or filters -> frontend re-calls /api/recommendations with updated params (sliders are disabled in Easiest mode since weights are auto-managed).
5. Student adds courses to cart -> POST /api/schedule/generate -> CSP solver finds conflict-free schedules ranked by preferences.
6. Student exports best schedule -> POST /api/schedule/export/ical -> .ics download.
7. Student calls POST /api/plan -> PlanGenerator returns a semester-by-semester graduation roadmap.

6.5 Caching Strategy
All external API data flows through a three-tier cache (LRU in-process -> Redis -> PostgreSQL). Write-through on all layers; reads promote from lower to higher tiers. Stampede prevention (app/cache/stampede.py) uses a probabilistic early expiration to avoid cache stampede on popular keys near TTL expiration.
Data | TTL | Source
PlanetTerp GPA / reviews | 24 hours | Live PlanetTerp API on miss; nightly Celery batch refresh
PlanetTerp professor ratings | 24 hours | Live PlanetTerp API on miss
umd.io course descriptions | Permanent (Postgres) | Backfilled on first request, Celery sync at reg period
Section schedule data | Per registration period | umd.io ETL via Celery Beat
Grade distributions | 24 hours | Live PlanetTerp /v1/grades on each detail page load

9. Key User Flows

9.1 First-Time Setup
1. Student lands on homepage -> clicks "Get Started"
2. No login step — app is immediately accessible
3. Onboarding: selects major from a dropdown sourced from GET /api/majors (v3.1); track dropdown updates dynamically based on the chosen major; enters optional minor; uploads transcript
   - If the transcript parser detects a major name not in the seeded catalog, an amber warning is shown and the student must pick the closest match from the dropdown.
4. System parses transcript (text or PDF), extracts completed courses with credits and gen-eds
5. POST /api/audit runs -> student sees degree progress dashboard
6. POST /api/recommendations runs -> first personalized recommendation feed (Balanced mode by default)

9.2 Semester Planning Session (Balanced Mode)
1. Student views recommendation feed; adjusts weight sliders (maximize GPA, prioritize requirements, etc.)
2. Applies filters (department, level, GenEd, min GPA)
3. Clicks a course card -> full detail page (GPA chart, reviews, prerequisites with completion checkmarks, which requirements it fulfills)

9.3 Finding Easy Electives — All GenEds Done (Easiest Classes Mode)
Scenario: Bhavesh is a junior CS student who has completed all GenEd requirements. He needs 9 more elective credits to stay on track but wants minimal stress this semester.

1. Student opens the Recommendations page
2. Goal toggle at the top of the sidebar shows "Balanced" by default — student clicks "Easiest Classes"
3. Weight sliders grey out with a note: "Weights auto-tuned for easy GPA + online reviews. Switch to Balanced to edit."
4. Recommendation feed refreshes — results now include courses from KNES, LING, AASP, ASTR, and other departments with high average GPAs and reviews mentioning "fully online", "asynchronous", "no final exam", or "easy A"
5. Example top results: AASP100 (avg GPA 3.8, reviews: "fully online, never had to attend"), KNES289 (avg GPA 3.7, reviews: "easy A, no exams"), ASTR100 (avg GPA 3.6, reviews: "recorded lectures, asynchronous")

9.4 Finding Easy Electives — GenEds Still Unmet
Scenario: A sophomore CS student still needs to complete DSHU and DVUP GenEd requirements but also wants the easiest possible route.

1. Student opens Recommendations page
2. Switches Goal to "Easiest Classes"
3. The backend internally runs a degree audit, detects DSHU and DVUP are unmet, and narrows the candidate pool to only courses tagged with those GenEd codes
4. Results show only DSHU/DVUP-fulfilling courses — ranked by average GPA and ease-indicating review keywords
5. Example: AASP100 (avg GPA 3.7, fulfills DSHU + DVUP, reviews: "online and easy A") ranks #1; WMST200 (avg GPA 3.6, fulfills DSHU, reviews: "no attendance required") ranks #2
6. Student adds AASP100 alongside two major courses, generates schedule, exports iCal

9.5 Custom Preference-Tag Search
Scenario: A student knows they learn best from recorded lectures and cannot attend class regularly due to a part-time job.

1. Student stays in Balanced mode (wants balanced scoring, not just easiest)
2. Opens the sidebar preference tags section
3. Toggles "online" and "no-attendance" tags
4. Recommendation feed re-ranks: courses whose combined review text mentions async delivery or no attendance policy score higher in the Preference Match dimension
5. Student adjusts the Preference Match weight slider to 40% to further amplify the effect
6. Results surface CMSC389 (async offering), STAT100, and several ARHU courses confirmed remote in reviews
7. Student can still see the full score breakdown per card (GPA %, Requirement Fit %, Preference Match %, etc.)

9.6 Graduation Planning
1. Student navigates to degree audit -> sees remaining requirements per group
2. Submits POST /api/plan with max_credits_per_semester and priority courses
3. System returns a full semester-by-semester roadmap ("Fall 2026: CMSC330, CMSC351...")
4. Student uses plan to guide future registration decisions, combining with Easiest Classes mode for elective slots

9.7 Schedule Building After Course Selection
1. Student has added 4 courses to cart (mix of required and easy electives)
2. Navigates to Schedule Builder page -> clicks "Generate Schedules"
3. CSP solver returns 3 ranked conflict-free schedules with preference scores
4. Student previews each schedule on the week-grid calendar view
5. Chooses the MWF-only schedule -> clicks "Export iCal"
6. Downloads .ics file -> imports directly into Google Calendar; 16 weeks of recurring events appear automatically

11. Risks & Mitigations
Risk | Impact | Mitigation
PlanetTerp API downtime | High | Circuit breaker fast-fails after 5 failures; 3-tier cache serves stale data; nightly batch refresh ensures freshness
Degree requirement data stale | Medium | Requirements are version-controlled Python code; flag if catalog year changes
umd.io API lag / deprecation | Medium | Direct umd.io fetch on miss; description persisted to Postgres on first fetch
Incorrect prerequisite mapping | High | "Report Issue" button planned; manual review queue for corrections
Redis unavailable | Low-Medium | LRU cache (layer 1) and Postgres cache (layer 3) maintain service degraded
Low initial adoption | Medium | Launch with CS community first; post on r/UMD and UMD CS Discord
Transcript parser edge cases | Low | Comprehensive regex with 63 test cases; AP/transfer credit handling implemented
Easiest mode sparse review data | Low-Medium | Soft boost design ensures courses without matching review keywords still surface if avg_gpa is high
Full-catalog candidate set too large | Low | Course table bounded by UMD catalog (~5,000 courses); Python filtering is fast; top_n default of 20 caps response
